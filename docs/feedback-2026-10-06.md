# Review feedback, 2026-10-06 — triage

_What was asked for, what already exists, what was decided, and where each piece lands._
_Source: review of the running site. Decisions marked **Zen** were taken on the spot._

The feedback has one question behind it, and it is the one the site should answer:

> **"What is coming up that I could bid on?"**

Items below are grouped by how far they are from that question, not by the order they were raised.

---

## 1. Already built — the gap is display, not capability

| Asked for | What exists today |
| :--- | :--- |
| "TOR should have a status — draft, finished, whatever it is now" | Every record carries `torStatus`: `announced` (ประกาศ) · `closed` (ปิดรับ) · `awarded` (ประกาศผู้ชนะแล้ว) · `cancelled` (ยกเลิกแล้ว). Search and the detail page already badge it |
| "TOR should have a deadline, which e-GP does not give you" | `deadline` is an extracted field, and the submission deadline is published in the **ประกาศเชิญชวน**, not in the TOR draft — which is why the TOR alone so often has none |
| "If we show a date the original does not have, it breaks" | Already prevented by design: a value borrowed from another document records `fromDocument`, and a value published by the source system rather than read by the model records `origin: "source"`. Nothing can present a borrowed date as if the TOR stated it |

**Nothing to build for the deadline mechanism itself.** What is missing is that the screens do not yet
*say* where a deadline came from, and the invitation state is not a first-class status (§2).

## 2. Decided, and small

| # | Decision | Why |
| :--- | :--- | :--- |
| D1 | **No ThaiD sign-in, and no national ID or tax ID stored anywhere.** Public email/password and ordinary OAuth only (Zen) | Keeps the platform off government identity infrastructure, and PDPA data minimisation means never holding an identifier the service does not need |
| D2 | **One save action, not two. Bookmark stays; star is removed** (Zen, choice delegated) | The profile already reads "เตือน TOR ที่บุ๊กมาร์กใกล้หมดเขต" — the copy was written for bookmarks, and a bookmark is the one that carries the deadline reminder |
| D3 | **"Has an invitation to bid" becomes an explicit status**, shown wherever a TOR is listed, so a reader can tell at a glance which projects are actually open to bid on and which are still only a draft scope (Zen) | A TOR without an invitation cannot be bid on yet. That distinction is the difference between "interesting" and "act now" |
| D4 | **A deadline is shown with its source.** From the invitation when the invitation supplies it, labelled as such; from the TOR when the TOR states it; otherwise "ไม่ระบุในเอกสาร" | Answers the ask without ever contradicting the original — the failure the feedback called out |
| D5 | **A vendor's budget interest is a preference with its own bounds**, not the corpus's range (Zen) | Done — a filter is rightly bounded by what exists; a stated preference must not change because this month's documents are cheaper than last month's |

## 3. New work, in order of how directly it serves the question

### 3a. Make "what is coming up" answerable without an account

- **Invitation status** (D3) — a status for "มีประกาศเชิญชวน" vs "ยังไม่มี", on the record, in search, and as a filter.
- **Deadline with provenance** (D4) — show the date, where it came from, and nothing when the documents do not state one.
- **ปีงบประมาณ (budget year)** — not stored today. The BMA e-GP search already has a budget-year parameter, so the source can supply it; it then becomes a filter and a column.
- **Filters: important first, and shorter.** The panel is long enough that everything below the first group starts off-screen. Agency has already moved to the bottom; the rest needs an order argued from what a vendor actually filters by first — plausibly deadline, then category, then budget.
- **Separate the two reading modes.** "Closing soon" is a different question from "search everything", and the site currently only offers the second.

### 3b. Needs accounts and matching — none of this exists yet

These all depend on slice 4 (`FR-D` profiles and auth, `FR-C` matching). They cannot be built on the
current code, and should not be promised before it.

- A **signed-in dashboard**: work on hand, what is closing soon, and TORs matched to this vendor.
- **Matched TORs shown on that dashboard**, which is what makes an account worth creating.
- **Search ranked by relevance to the signed-in vendor first, then by nearest deadline.** Today search
  has no notion of who is asking.
